# 当前状态

更新于 2026-09-10。这一页只记「实际做完并实际验证过的」。人工演示、单元测试、真实 PostgreSQL
验证和 KaiSpan 正式接入是不同层次，不互相替代。

## 做完的

### 骨架（`onboarding.md` 的第一个检查点）

- `apps/api`（NestJS 11 + Prisma 7）、`apps/web`（Next.js 16 + React 19）、`tools`、`docs`、
  `references`。pnpm workspace，strict TypeScript。
- Prisma schema 13 个模型。属于公司的带 `organizationId`，属于门店的同时带 `unitId`；
  已提交记录只作废不物理删除；模板按版本存，记录锁自己那一版。
- `ContextService.resolve()` 是全后端唯一一处「你是谁」的判定。请求身上只带登录凭证。
- 权限只走 `canFillHaccp()`（沿用 `operations.haccp.fill`）和 `canManageHaccp()`，
  接口用 `@RequireHaccpFill()` / `@RequireHaccpManage()` 声明。业务代码里没有散落的角色判断。
- 查询一律拼 `unitScope(ctx)`，跨租户的 id 直接查不到，而不是查到之后靠一句 if 拦住。

### 第一批业务闭环

**判定逻辑**（`src/domain/`）。临界值判定、条件限值（出餐温度按热菜/冷菜切、入库验收按商品
类别切）、短暂容许区间、选项超标、清单全项通过、周期与「还差几次」的推导。这些在后端 ——
前端会先判一次给即时反馈，但能不能提交由后端说了算。

**派单**。派给班次不点名，责任人当天从班表推导。班表改了派单自动跟着改。改派从指定日期起
生效、旧规则当天封口，所以上个月的记录不会被算成「本来该另一个人填」。一个班两个人时两边
待办都出现，谁先提交算谁的，填完从另一个人那里消失。每周 N 次的表每天出现、标着「本周还差
N 次」，够了本周不再出现。

**填表闭环**。草稿（只有本人看得到，不进店长列表、不判超标）、提交、必填拦截、超标时纠正措施
必填、补填要写原因且至少 5 个字、不能给还没到的日子填表。草稿转正不留孤儿。

**作废重填**。员工能作废自己提交的，店长能作废本店任何一条，理由必填，作废是标记不是删除，
默认隐藏可切换显示。

**店长处理异常**。正常记录提交即完成，不做两级签署。待处理按「哪台设备的哪个测量点」聚合，
连着几天的同一个问题算一件事并打「连续 N 天」标 —— 那是设备故障的信号，不是 N 件待办。
温度类超标必须挂到设备开维修单，写一句处理结果关不掉；填了维修结果、标记完成，异常才闭环，
设备没有未完成的维修单时自动回「正常」。挂不上设备的异常（害虫、退货）写处理结果即完成。

**设备台账与温度趋势**。单序列时间线 + 临界值带 + 超标点，超标点用颜色、尺寸、白色描边环三重
编码，只标首尾和最严重的那个，附一张可展开的数据表供读屏和打印。员工只读看得到。

**漏填补救**。扫过去 7 天的每日表，按表聚合列出空着的日子，一键去补。

**最小班表**。开店 / 中班 / 收店三个班次，时间可改，一周一屏。派单靠它推人。

**月度表**。跟纸质原表同一个版式：月度网格一天一行、流水表一条记录一行，表头带
Operation / Inspector（培训表另有 Referent / Topic），表底带临界值与纠正措施说明。
超标格做三重编码 —— 颜色、一个 `!`、打印时的黑色粗边和网点底纹，因为打印出来是黑白的，
只靠红色等于没标。漏填的日子画斜线底纹；今天还没填单独一种状态，不算漏（截止点是当天午夜）；
还没到的日子灰掉。空月份不画 31 行空网格，一句提示加一个「去填这张表」。

**检查模式**。一次给出这个月全部七张表，只读、页内零个操作按钮，屏幕转过去就能给检查员看。
带封面（公司 / 门店 / 期间 / 表单数 / 记录数 / 生成时间），打印时每张表另起一页。
顶部有一段「检查前先补这几处」，列出本月缺记录的表 —— 那是给店长看的，打印件里不出现。

**前端**。登录、员工端「等你处理」、店长主页、填表页（即时判定 / 草稿 / 纠正措施 / 补填原因）、
记录列表与详情（含作废）、异常处理页、设备与趋势、班表与派单。业务数据全部走 NestJS API。

## 已知的环境限制

- `binaries.prisma.sh` 在这套开发环境里连不上，所以 migration 走 `tools/migrate.mjs`
  而不是 `prisma migrate`。理由和影响写在 README「关于 migration」。
- 代码只在 Linux 上跑过（x86_64 与 aarch64 各一台）。`embedded-postgres` 的 macOS 二进制
  已经列进 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies`，但没有在 macOS 上实际验证。
- 不要把工作副本放在网络挂载或 FUSE 挂载的目录里跑。pnpm 的软链 node_modules 加上 Prisma CLI
  会同时打开大量文件，挂载层的句柄上限撑不住，`prisma generate` 会报 EMFILE。放在本地磁盘上
  就没有这个问题。
- 以 root 身份跑 `pnpm pg:start` 时，`embedded-postgres` 会切到 `postgres` 用户去起数据库，
  项目目录和 `node_modules` 需要对该用户可读可执行。普通用户没有这个问题。
