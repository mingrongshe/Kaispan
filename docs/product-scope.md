# HACCP 模块产品范围（第一版）

事实来源是 `references/haccp-prototype.html` 与本文。原型已经明确的行为直接照抄，本文只在原型
没说清楚的地方补上产品负责人确认过的规则。任何还没确认的写在最后一节「待决定」，不当成既定规则用。

产品负责人：Zola（Mingrong）。确认日期：2026-09-10。

---

## 一、第一版目标与非目标

第一版要做到的是：一家门店的员工和店长在真实的一周里能靠这个模块完成 HACCP 记录，而不是
演示一遍。员工在自己手机上打开当天派到自己头上的表，填，提交；店长在电脑上排下一周的派单、
处理超标、把月度表打印出来给卫生局。刷新、重新登录、换一台设备，记录都还在 PostgreSQL 里。

第一版不做的是：接入 KaiSpan 平台底座、多门店切换、通知与提醒推送、报表与统计分析、
通用表单平台、工作流引擎、完整 RBAC。演示只跑一家公司一家门店，但数据归属字段按
`docs/kaispan-compatibility.md` 全部保留。

---

## 二、用户与职责

只有两个角色。

**员工（employee）** 做一件事，打开派给自己的表，填写，提交。他还能只读地翻本店任何一张表的
历史记录，因为量温度这件事本身就要和昨天对照。他不能改别人的记录，也不能处理异常。

**店长（store_manager）** 做四件事。排下一周的派单；处理超标记录；维护表单模板、设备台账和
最小班表；把月度表和检查汇总打印或导出给卫生局。他也可以自己填表，包括替不在场的人代录。

---

## 三、典型工作流程

**周日晚上，店长排下一周。** 派单的单位是班次，不是人。店长写「储存 / 冷藏温度归开店班」，
那一周每天谁上开店班，这张表当天就落到谁头上。班表后来改了，派单自动跟着改，店长不用重排。
一个班上排了两个人时，两个人的待办里都会出现这张表。

**周四早上，员工填表。** Olivia 六点半上开店班，手机上「等你处理」里出现「储存 / 冷藏温度」。
她量吧台三个冷柜，冷库那两个进不去，先存草稿。草稿只有她自己看得见，不进店长的列表，也不判
超标。送货的走了之后她量完剩下两个，提交。冷藏柜 2 是 8.6°C，超上限 7°C，那一格当场标红，
纠正措施区展开，不写不让提交。她写「已调低设定并报修」，提交。

**同一天，店长处理。** Martin 的「等你处理」里出现这条超标。这是温度类，必须挂到一台具体设备
（冷藏柜 2）并开一张维修单。维修单填了处理结果、标记完成，这条异常才算闭环。害虫防治发现
活体、入库验收退货这类挂不到机器上的异常，店长写处理结果就算完成。

**周六，补漏。** Martin 在主页看到周四的「清洁与消毒」空着，让 Olivia 补。补填的记录日期仍是
周四，但标着「补填」，并且必须写为什么当天没填。

**季度末，卫生局来人。** 店长打开检查模式，一次给出这个月全部七张表的只读汇总，或者把月度表
打印出来。打印件固定是德语。

## 四、页面与业务动作

页面沿用原型，不重新设计。

| 页面 | 谁用 | 主要动作 |
|---|---|---|
| HACCP 主页 | 店长 | 看今天要填的、漏填的、待处理的异常；逐张派单；进各个子页 |
| 填表页 | 员工 / 店长 | 填写、存草稿、提交；超标时填纠正措施；改日期补填 |
| 员工待办 | 员工 | 看派给自己的表，点进去填 |
| 全部记录 | 店长 / 员工（只读） | 按表单、月份、状态筛选；分页；CSV 导出 |
| 月度表 | 店长 | 按原表版式的月度网格；打印（A4 纵向）；CSV 导出 |
| 检查模式 | 店长 | 只读、无操作按钮的整月汇总，带封面，逐表分页打印 |
| 表单管理 | 店长 | 表单列表；停用与启用；进编辑器 |
| 表单编辑器 | 店长 | 改测量点（改名、增删、改类型与单位、改临界值、排序）；保存生成新版本 |
| 设备台账 | 店长 | 设备列表与详情；关联测量点；开维修单、填结果、标记完成；温度趋势图 |
| 最小班表 | 店长 | 维护「谁哪天上哪个班」（开店 / 中班 / 收店），供派单推导责任人 |

原型里的「主页行内快填」是否保留见待决定。

## 五、表单字段与校验

七张表照原表录入，列结构和临界值来自 `references/haccp-prototype.html` 里的
`haccpTemplates()`，不重新发明。三种版式：月度网格（monthly-grid）、流水记录（log）、
培训记录（training）。每张表表头有 Operation 与 Inspector，员工培训表另有 Referent 与
Training topic，两项必填。

| 表 | 版式 | 频次 | 测量点 |
|---|---|---|---|
| 储存 / 冷藏温度 | 月度网格 | 每日（开店前） | 冷藏间、冷藏柜 1、冷藏柜 2、冷藏 1、冷藏 2，各 +4~+7°C |
| 清洁与消毒 | 月度网格 | 每日（收店） | 执行人、方式 R/D、销售区、备餐区、仓库、设备区域、厕所 |
| 加热温度 | 流水 | 每周 2 次 | 产品、实测核心温度（≥70°C） |
| 出餐温度 | 流水 | 每周 2 次 | 菜品类型、产品、出餐温度（热菜 ≥65°C，冷菜 ≤7°C） |
| 入库验收 | 流水 | 每周 2 次 | 供应商、商品类别、实测温度（按类别取限值）、感官检查（全项必过）、发现的问题 |
| 害虫防治 | 流水 | 每周 1 次 | 备餐区、冷藏储存、仓库、销售区，「有痕迹」或「发现活体」算异常 |
| 员工培训 | 培训记录 | 每年至少 1 次 | 参与人、培训类型（初次 / 复训）、签名 |

校验规则三条。第一，所有测量点默认必填，只有编辑器里明确设为选填的才可以空着。第二，温度类
按 `limit`（min / max / tolerance）判定，出餐温度和入库验收按另一列的取值切换限值
（`limitBy`），选项类按 `breachOn` 判定，清单类要求全项通过（`requireAll`）。落在
tolerance 内的算警告不算超标。第三，只要有任何一项判为超标，纠正措施变成必填，不填不能提交。

临界值是模板里的可编辑配置，不是写死的法规常量。条件限值（`limitBy`）在编辑器里只读，
沿用原型的处理方式。

## 六、状态与修改规则

一条记录的状态只有四种：草稿、已提交、有异常待处理、已处理。另有一个正交的「已作废」标记。

**草稿** 由员工保存，只有他自己看得到，不进店长的任何列表，不参与超标判定，不算这张表当天
填过。一个员工对同一张表同一天只有一份草稿。

**已提交** 是提交后没有任何一项超标的记录。提交即完成，店长不需要逐条签字。原表上的
Control / Signature 两级签署在第一版不实现。

**有异常待处理** 是提交后至少一项超标的记录。它进店长的待处理队列。

**已处理**。温度类异常必须挂到一台设备并开维修单，维修单标记完成时这条异常转为已处理。
其余异常由店长写处理结果转为已处理。两种情况都记录处理人和处理时间。

**作废**。员工可以作废自己提交过的记录并重填，必须写理由。店长可以作废本店任何记录，同样必须
写理由。作废是标记不是删除，原记录留痕、默认隐藏、可切换显示。已提交或经店长处理的记录一律
不做无痕物理删除。

**补填**。过了记录日期的午夜还没填就算漏填。漏填仍然可以补，补出来的记录日期还是原来那天，
但带「补填」标记和实际提交时间，并且必须写为什么当天没填。界面上和给卫生局的导出件里都看得见。

截止点是记录日期的午夜，与员工上早班还是晚班无关。

## 七、权限与可见范围

员工只能打开真正派给自己的表。别人的表、别人的草稿一律进不去，直接用记录 ID 也不行。

员工能只读地看本店任何一张表的全部历史记录，包括同事填的，同事姓名会出现在记录上。他不能修改
别人的记录，不能处理异常，不能进表单编辑器、设备台账和最小班表。员工是否能看设备详情和趋势图
见待决定。

店长能看和处理本门店的全部记录。跨门店一律看不到，即使第一版演示只跑一家店。

界面语言跟员工档案里的沟通语言走，中文或德语，一人一种。打印和导出给卫生局的文件固定德语，
与界面语言无关。员工自己填进去的自由文本不做机器翻译。

## 八、异常场景

**填错了。** 员工自己作废重填，写理由。原记录留痕。

**忘了填。** 过了午夜进漏填，店长主页上按表单聚合列出漏掉的日子。补填时标「补填」并写原因。

**店长忘了排下周。** 派单落到班次上，班表在就有责任人；班表也没排的日子，那张表当天没有责任人，
店长主页上显示为没人认领，他自己补排或自己填。

**排的人当天不在班。** 派单不点名，责任人是当天从班表算出来的，人换了自动跟着换。班表上那天
一个人都没有时，系统提示店长这张表没人接。

**一个班上两个人。** 两个人的待办里都出现，谁先提交算谁的，记录上签先提交那个人的名字，另一个
人的待办自动消失。

**设备真的坏了。** 同一台设备连续多天同一个测量点超标时，主页把它们聚成一条，标明连续天数，
直接指向那台设备的详情和维修单，而不是列成几条独立的待办。

**表单改版之后看旧记录。** 模板按版本存，记录带版本号，渲染走记录自己那一版，旧记录不会被新
列名串掉。已经有记录的表单不能物理删除，只能停用并归档。

## 九、第一版业务验收场景

按顺序走通下面这一条，第一版才算达到可试用。

1. 店长排下周：把「储存 / 冷藏温度」派给开店班，在最小班表里排周四 Olivia 上开店班。
2. Olivia 登录，周四的待办里出现这张表，点进去。
3. 她填三个冷柜存草稿，退出再进来，草稿还在，店长那边看不到这份草稿。
4. 她填完五个，其中冷藏柜 2 超上限，那一格标红，不填纠正措施提交按钮不亮。
5. 填了纠正措施，提交成功。刷新页面记录还在。
6. 店长登录，待处理里出现这条超标，正常的那几条不需要他点。
7. 店长把它挂到冷藏柜 2，开维修单，填处理结果，标记完成，这条异常转为已处理。
8. Olivia 再打开，看到这条记录的最终状态；她也能只读翻到前一天的温度。
9. Olivia 发现自己抄错了一个数，作废重填，写理由，原记录变灰留痕。
10. 店长打开这个月的月度表，看到周四那一行，打印预览是德语。
11. 周六补填周四漏掉的「清洁与消毒」，记录标「补填」，写了原因。

另外三条属于技术边界，写在 `docs/acceptance.md` 里：员工调用店长管理接口被拒；跨
organization 读不到；跨 unit 读不到。

## 十、待决定

下面这些还没确认，实现时不能自行补成规则。

1. **非每日表的派单单位。** 「派给班次」是围绕每日表定的。加热温度、出餐温度、入库验收（每周
   2 次）、害虫防治（每周 1 次）、员工培训（每年 1 次）派给哪个班次、周进度怎么和班次结合，
   还没定。
2. **员工培训表由谁填。** 表头要填讲师和培训主题，参与人是一份名单，和「派给一个班次」的模型
   不一样。
3. **清洁与消毒表里的「执行人」列和表头 Inspector 是不是同一个人**（原 PROJECT_LOG 的 D11）。
   暂按两个人处理。
4. **草稿能不能删。** 兼容边界把这一条留给产品范围决定，还没定。
5. **补填必须写的原因是自由文本还是选项。** 暂按自由文本。
6. **员工能不能看设备台账、设备详情和温度趋势图。** 目前只确认了员工能只读看记录历史。
7. **哪些列可以拍照。** 已确认照片附件进第一版，但没定哪几张表的哪几列开放。
8. **主页行内快填是否保留。** 原型有，第一版范围里没单独确认过。
9. **最小班表的班次种类。** 暂按开店 / 中班 / 收店三种，是否够用没确认。
